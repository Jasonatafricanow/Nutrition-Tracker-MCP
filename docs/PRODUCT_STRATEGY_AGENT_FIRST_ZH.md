# 决策记录：从专业精确追踪转向低门槛、可回溯的日常健康管理

日期：2026-10-18。适用对象：Nutrition Tracker MCP（含家庭 NAS 模式）。这是一次**务实的产品定位纠偏**，不是否认营养测量、医学研究或专业训练的准确性要求。

## 专业能力先呈现，日常使用允许主动降级

初次接触时，完整的专业面板与训练、营养、恢复分析能力能让用户看到健康管理可能达到的深度，建立开始使用的动机。**展示高级能力**不代表强制用户按运动员标准称量每一餐，更不代表初次使用必须填写专业档案。

之后若用户不再坚持碳循环、TDEE 等高成本管理，留下来的睡眠、体重、活动、简单饮食记录并非失败，而是可持续的真实需求。允许主动切换到日常视图，保留已有数据、回溯和专业功能的再次开启。**不按不活跃时长自动降级**，也不把日常模式当成删减数据精度或科学真实性的借口。

当前最小实现：Dashboard 默认展示专业能力，仅提供一个可逆的「日常／专业」显示切换；Agent 尊重用户表示的使用深度，不建立额外的行为预测、积分激励或强制新手流程。

## 用户与目标

默认面向**刚开始培养健康管理习惯的普通人**，而不是运动员、健美选手或临床用户。营养、睡眠、活动、心率等数据为自我观察、趋势回顾和日常安排提供参考，不构成医疗指导。碳循环、动态 TDEE、补剂及高级训练设置继续保留，但不作为普通用户开始记录的前提。

主要输入界面是 Agent/MCP；Dashboard 用于浏览、发现不合理的值和手工校准。家庭版让 Agent 顺带消费同一 NAS 上的家庭状态，而非开发独立健康社交或通知系统。

## 为什么我们选择容忍合理误差

人对一份家常菜的克重、食用油和烹饪损耗本来就难以精确测量。让模型反复问食材来源、熟重、份量和宏量成分，可能减少某次误差，却把用户的日常输入变成繁琐维护。若与 Agent 交流超过约三轮，很多任务的时间成本已经不如直接操作手机 App；持续使用的意愿也会下降。

**我们优化的是日常行为的总成本，而非单次记录的表面精确度。** 一份明确标注为估算的餐食，通常比因为流程繁琐而完全没有记录更有长期观察价值。这里不设未经实测的统一误差容忍百分比，也不声称模型推断可以替代称量。

产品原则：
1. **默认低轮次记录。** 文字描述要求记餐时，允许一次用户表达后直接估算入账。**照片默认先识别并简要汇报一次，让用户对食物种类和大致份量作一次整体确认**，确认后立即入账；不得逐项进行多轮审批，也不能把鸡蛋误认成香蕉还未经核对就落账。内部可有多次 MCP 调用，但不应扩大用户交互轮次。
2. **估算可以直接入账，但必须保留来源。** 分清照片/语言推断、用户估算、食品库匹配和实测。不把推断包装为测量事实。照片仅用于 Agent 观察；不要求把原图存进服务器。
3. **随时可纠错、可回溯。** 「刚才米饭更多」「昨天那一餐记错了」应定位原记录并保留修订历史，不通过重复新增一餐解决。Dashboard 也支持直接编辑。
4. **只在实质性歧义时追问。** 无法确定记录的是谁、哪一餐，或明显可能误记时再提问；不要为普通克重偏差发起审查流程。
5. **普通观察不能自动驱动高精度校准。** 未测量的估算餐食不应被假装成严格的能量收支证据，更不能因一次估算自动修改 TDEE、训练计划或给出临床结论。
6. **不追求盲目合并 MCP 工具。** 用户交互次数、模型工具选择准确率、失败重试、Token 与后台调用共同衡量。两个通用工具并不天然优于三个结构清晰的工具。

## 先前设计与此次纠偏

原先照片路线要求 `stage_photo_estimate` 后逐项确认 `confirm_photo_meal`，对普通用户负担偏高。但**照片种类误识别比克重误差更需要在写入前拦截**。因此保留现有照片草稿和确认接口，把前端交互压缩成「识别食物种类及估算份量 → 一次整体确认或纠正 → 写入」；无需用户逐项审核底层 JSON，Agent 自动组装确认后的 decisions。日常文字记录增加 `quick_meal`，允许一次入账，但照片不得绕过上述预览。不能为减少轮次而绕开 SQLite 原子性、请求幂等或校正历史。

家庭版曾误把 NAS 当作多租户 SaaS，增加成员令牌和逐项审批；已主动回滚并记录于 [PROJECT_RECORD_ZH.md](PROJECT_RECORD_ZH.md)。这一转向与家庭权限纠偏一致：**技术约束应该服务于目标用户和实际场景，而不是反过来增加使用负担。**

## 后续迭代（低摩擦优先）

本轮继续复用现有能力：最近一餐纠错按食物名定位而非向用户索要 mealId；家庭菜谱直接汇总既有餐食模板；7/30 天简报只计算有证据的日期；条码查询仅把外部食品作为带来源的候选，不强制新建食材。真正的用户交互轮次、模型填参准确率仍需 Agent 实测，不能只靠单元测试认定已解决。

## 可验证的验收标准

- 文字记录：用户清楚要求记餐时，尽量一次表达完成估算入账。照片记录：一次识别预览＋用户一次整体确认，然后写入并回复「已记录、估算、可修改」，不能先落账再补问确认。
- 估算写入保留来源、时点、餐食 ID 和份量来源；重复 `requestId` 不重复记账。
- 用户可通过 Agent 或 Dashboard 修改原记录，保留版本与变更审计。
- 家庭成员设备可自动同步晨间健康指标，按 `memberId` 落入正确账本，已有单人模式仍可使用；失败或未知成员不能悄悄写入其他人。
- 对真实 Agent 轨迹测量：用户轮次、MCP 调用数、任务完成率、错误修正率和每任务 Token。没有这些数据，不宣称交互效率已被真实验证。

## 适用边界

这种低摩擦估算适合日常自我观察；临床监测、药物剂量、疾病风险评估、竞技营养等高影响任务不适用此默认模式。涉及事实缺失或明显安全问题仍应说明不确定性或建议求助专业人员。

**核心判断：低门槛录入、合理误差可容忍、保留来源、随时纠错。准确性重要，但不能以消灭用户持续记录的意愿为代价。**
