# PhotoEstimate v1 — blind, weighed-photo evaluation

**Purpose:** evaluate the *visual Agent's* food identification and edible mass estimates, not merely the JSON schema or successful MCP tool calls. Keep this benchmark **outside** the production nutrition ledger: testing must not modify a user's nutrition log or TDEE estimate.

## Why three separate inputs?

1. `references.json`: independently weighed **truth**, including foods that are genuinely hidden by the photograph. Keep this file and original photos private.
2. `predictions.json`: unmodified, machine-readable `nutrition.photo_estimate.v1` output generated by a vision Agent **without seeing reference weights**. Include `run.modelId`, `run.promptSha256`, and `run.referencesHiddenFromAgent: true`. Use the same fixed image set across prompt/model comparisons.
3. `reviews.json`: a human's item-by-item correspondence adjudication, written *after* the predictions are frozen. Text string similarity is insufficient: “rice” vs “cooked rice” may be fine, “fish” vs “chicken” is not.

The scorer refuses mismatched cases, unreviewed predicted items, duplicate reference assignments, impossible mass intervals and unversioned inputs. It does **not** inspect photo pixels or infer a food's identity. The runtime intake compiler and its `photoEstimateSchema` independently validate tool inputs; this scorer is a separate evaluation utility, not a replacement for schema validation.

## First run (synthetic fixture **only**)

```bash
node audit/eval-photo-estimates.mjs --example
node --test test/photo-benchmark.test.js
```

The three committed sample files under `benchmark/examples` are **hand-written synthetic unit fixtures, not photos or model predictions**. Any accuracy figures printed by `--example` only prove the metrics code works. **Do not publish their scores as model performance.**

## Collect a real, blinded evaluation set

- Start with **20–30 separately weighed meal photos** across unfamiliar dishes, overlapping items, mixed foods, different lighting and no-scale images. This is an engineering smoke benchmark, **not** a statistical validation sample. Increase coverage after first failure analysis.
- Weigh each edible ingredient/portion independently *before* plating, record raw vs cooked, and document whether it is entirely visible. If the user takes a photo of a partly eaten plate, log **what was actually consumed** independently; do not relabel the remainder as consumption.
- Take a photo as an ordinary user would. For some cases include a verified-size object or measured bowl; for others do not provide a scale. Record preparation/cuisine and camera condition privately.
- Collect immutable, blinded Agent responses using the exact `estimate_meal_photo` MCP prompt. Store JSON without correcting the model's guesses. Record the **exact** model ID and prompt SHA256 (compute over the actual prompt text, not this Markdown).
- Only after predictions have been frozen should a human match each predicted item to a weighed reference item and mark identity `correct`, `broad`, `wrong`, `unmatched`, or `unjudgeable`. Multiple predicted fragments must not match the same weighed component.
- Evaluate the same cases with any challenger prompt. Analyze failures by hidden oil/sauce, mixed dish, raw/cooked ambiguity, missing scale, unrecognized food and portion bias before editing the prompt.

### Private JSON file format

Use `benchmark/examples/references.json`, `predictions.json` and `reviews.json` as **structural examples only**. Each file contains `schemaVersion: "nutrition.photo_benchmark.v1"` and a `cases[]` array keyed by identical `caseId` values.

`references.json`: `datasetKind: "weighed_photos"`, and each case has `referenceItems[]` with `id`, `name`, `grams` (actual edible mass), `visible` (whether the item could be seen). Hidden oil can be explicitly represented with `visible: false`. Do not share a private user's photos or personal health details.

`predictions.json`: `run: {modelId, promptSha256, referencesHiddenFromAgent:true}` plus `cases[]` containing the immutable `estimate`. Preserve the full PhotoEstimate v1 IR, including abstentions (`not_estimable`) and uncertainty bounds.

`reviews.json`: one `assignments[]` entry for **every** predicted item. `predictedId` points to the model item; `referenceId` is the measured reference ID, or `null` for `unmatched`/`unjudgeable`. `identity` is one of `correct`, `broad`, `wrong`, `unmatched`, `unjudgeable`. `broad` credits defensible category-level recognition separately from exact classification. `wrong` remains wrong even if its mass accidentally agrees.

```bash
node audit/eval-photo-estimates.mjs \
  --references benchmark/private/references.json \
  --predictions benchmark/private/predictions.json \
  --reviews benchmark/private/reviews.json \
  --output benchmark/private/report.json
```

Store `benchmark/private/` outside source control. The CLI outputs only numerical scores and anonymized `caseId`-keyed diagnostics, never photo binaries or raw labels.

## Measurements and interpretation

| Metric | Meaning | Caveat |
| --- | --- | --- |
| Identification precision / recall | Human-reviewed `correct` + `broad` vs predictions / visibly weighed items | Splitting one food into multiple predictions, unmatched items and missed foods lower scores |
| Strict recognition recall | Only `correct` matches count | Reports broad-but-acceptable names separately |
| Mass MAE (g) | Mean absolute gram difference for *identifiably matched* portions with a numeric estimate | Not calculable for wrong or abstaining items; always report scored sample count |
| Weighted absolute percentage error | Total absolute mass error / total actual mass of scored items | Does not measure energy/nutrient error |
| Interval coverage | Portion of scored ground-truth masses falling between predicted min/max | Extremely wide intervals cover trivially; inspect mean interval width too |
| Abstention rate | Portion predictions that explicitly return `not_estimable` | Correct abstention can be preferable to fabricated precision |
| Hidden-item flag rate | How often a photo with invisible weighed items contains *any* warning | Generic warnings can game this metric; manual review is still necessary |

Results are stratified by the Agent's declared scale-reference class. This classification is itself a model output and should be independently checked. **Do not** compare only non-abstaining cases when reporting model improvement; monitor recognition coverage, abstention, and interval width together. Short intervals with low coverage suggest overconfidence; extremely wide intervals with high coverage may be unhelpful.

## Acceptance gates (engineering quality, not clinical thresholds)

- Evidence separation: no ground-truth weights or food labels shown to the Agent before prediction; immutable prediction artifacts and human reviews remain auditable.
- No unreviewed images silently disappear; incorrect identity does not enter gram MAE as a plausible weight.
- `not_estimable` stays null and never silently changes into a gram guess.
- Zero photos, no verified truth, or missing adjudications -> **no performance claim**. Numerical thresholds should be selected only after obtaining a nontrivial real dataset and a simple baseline, not retrofitted to synthetic examples.

**Known limitations:** a mass-only benchmark cannot validate calorie accuracy without a trusted nutrition database and preparation method; weighed food photos are still a selected sample; sauces, oil and occlusion are difficult to ground independently. Estimating food mass from a single RGB photograph without calibrated scale or depth remains underdetermined.
